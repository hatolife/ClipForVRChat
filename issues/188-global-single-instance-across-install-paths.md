# 別パス/別バージョンを含めてClipForVRChatを単一起動にする

## 問題

ClipForVRChatはVRChat OSCの受信/送信ポートを使うため、同時に複数起動するとOSC portの競合や、どのプロセスがOSC状態を扱っているか分からない状態が起きる。

現状は `.lock` による同時起動制限が入っているように見えるが、別のパスに置いたClipForVRChatや、別バージョンのClipForVRChatは起動できてしまう。これにより、同じPC上で複数のClipForVRChatが同時にOSCを扱える状態になっている。

## 期待する挙動

ClipForVRChatは、実行ファイルの配置パスやバージョンが違っていても、同じWindowsユーザー環境では原則として1つだけ起動する。

管理者権限で起動された場合は本体処理を開始せず、「管理者権限では起動できません。通常のユーザー権限で起動してください」のような内容のダイアログを表示して終了する。

新しく起動しようとしたときに既存のClipForVRChatが起動中であれば、利用者に分かるダイアログを表示し、次の操作を選べるようにする。

- 既存のClipForVRChatを閉じて、新しく起動したClipForVRChatを続行する。
- 既存のClipForVRChatをアクティブにして、新しく起動したClipForVRChatを終了する。
- 必要に応じて、何も変更せず新しい起動をキャンセルする。

## 受け入れ条件

- 別フォルダにある同一バージョンのClipForVRChatを同時起動しようとしても、単一起動制御が働く。
- 別フォルダにある別バージョンのClipForVRChatを同時起動しようとしても、単一起動制御が働く。
- 管理者権限で起動された場合、設定読み込み、OSC初期化、Wails UI起動、単一起動IPC処理へ進まず、通常ユーザー権限で起動するよう促すダイアログを表示して終了する。
- 単一起動制御は実行ファイル配置パスに依存せず、同じWindowsユーザー環境で共通の識別子を使う。
- 既存プロセスが起動中の場合、新規プロセス側で「既存を閉じて新規を起動」「既存をアクティブにして新規を閉じる」を選べる。
- 「既存を閉じて新規を起動」を選んだ場合、既存プロセスへ安全な終了要求を送り、終了確認後に新規プロセスが起動を継続する。
- 「既存をアクティブにして新規を閉じる」を選んだ場合、既存ウィンドウを前面表示し、新規プロセスはUI初期化やOSC初期化を進めず終了する。
- 既存プロセスが応答しない場合のタイムアウトとエラー表示がある。
- クラッシュ後に古いlock情報だけが残っても、起動不能にならない。
- OSC受信器や自動撮影初期化より前に単一起動判定が完了する。
- 既存の `.lock` 方式を使い続ける場合でも、別パス/別バージョンを横断して効く設計になっている。

## メモ

- #022 は同じ実行ファイルからの複数起動制限として完了済みだが、本issueでは別パス/別バージョンを含むPC内グローバルな単一起動制御を扱う。
- 実装候補として、Windows named mutex、ローカルIPC、既存ウィンドウのアクティブ化API、安全な終了要求APIの組み合わせを検討する。

## 実現可能性・実装方法調査

### 現状

- `src/main.go` の `acquireInstanceLock(configPath)` は `configPath` のディレクトリ配下に `ClipForVRChat.lock` を作り、`github.com/gofrs/flock` の `TryLock()` で二重起動を抑止している。
- この方式はロックファイルの場所が設定パスに依存するため、別パス/別バージョンで設定パスや実行環境が分かれると同じロックを見ない可能性がある。
- `--version`、`--help`、zip暗号化処理は現在もロック取得前に処理される。単一起動制御や管理者権限拒否を強化しても、これらのCLI用途をどこまで対象にするかは明示しておく必要がある。
- Wailsの `App.startup()` でOSC受信などの初期化が始まるため、グローバルな単一起動判定と既存プロセスへの引き継ぎは `runUI()` より前に完了させる必要がある。

### 実現可能性

- 実現可能。現在の「設定パスごとのlock」を「Windowsユーザー/セッション単位で共通の識別子」に置き換え、既存プロセスへ命令を送るIPCを追加すれば要件を満たせる。
- ロックだけなら固定パスのlockファイルでも対応できるが、「既存を閉じて新規起動」「既存をアクティブ化して新規終了」を実現するにはIPCが必要。
- Windowsでは名前付きmutexを単一起動の一次判定に使うのが適している。プロセス終了時にOSが解放するため、lockファイル単体よりも stale lock に強い。
- 管理者権限起動の検出と拒否も実現可能。Windows APIで現在プロセスがelevated tokenかを判定し、elevatedなら本体初期化前にダイアログを出して終了する。

### 推奨実装案

- 起動直後、GUI本体処理へ入る前に管理者権限かどうかを判定する。
  - 管理者権限の場合は、設定読み込み、単一起動mutex取得、IPC、OSC初期化、Wails起動へ進まない。
  - 表示文言は「管理者権限では起動できません。通常のユーザー権限で起動してください。」のように、ユーザーが次に取る操作を明確にする。
  - 実装候補は `golang.org/x/sys/windows` を使った `OpenProcessToken` + `GetTokenInformation(TokenElevation)`。
- CLI単体処理の扱いを決めたうえで、設定読み込み/OSC初期化/Wails起動の前に、ユーザー単位の名前付きmutexを取得する。
  - 例: `Local\ClipForVRChat.SingleInstance` のように、バージョンや実行パスを含めない固定名にする。
  - 複数Windowsユーザー間で互いに起動を妨げないよう、原則 `Global\` ではなく `Local\` を使う。
- mutex取得に成功したプロセスを既存インスタンスとして扱い、同一ユーザー内から接続できるローカルIPCサーバーを起動する。
  - Windows名前付きパイプが第一候補。代替として localhost TCP + ランダムトークンも可能だが、トークン管理とファイル権限に注意が必要。
  - `%LOCALAPPDATA%` 配下に `single-instance.json` のような状態ファイルを置き、PID、実行ファイルパス、バージョン、IPCエンドポイント、nonce/tokenなどを記録する。
- 後続プロセスはmutex取得失敗時に状態ファイルを読み、IPCで既存インスタンスへ接続して状態確認を行う。
- 後続プロセス側で選択ダイアログを出し、選択に応じてIPCコマンドを送る。
  - 既存をアクティブにして新規を閉じる: 既存プロセスへ `activate` を送り、既存側で `runtime.WindowShow()`、`runtime.WindowUnminimise()` などを呼んでから後続プロセスを終了する。
  - 既存を閉じて新規を起動: 既存プロセスへ `shutdown` を送り、既存側で通常の終了経路を通す。後続プロセスはmutex解放または既存プロセス終了をタイムアウト付きで待ち、取得できたら起動を継続する。
  - キャンセル: 後続プロセスを終了する。
- 既存プロセスが応答しない場合は、強制終了を既定動作にしない。再試行、終了、プロセスが存在しない場合のみstale状態として回復、のように扱う。

### 注意点

- 管理者権限のClipForVRChatと通常ユーザー権限のClipForVRChatを混在させると、設定ファイル、ログ、IPC、OSCポート、子プロセスの権限が不揃いになりやすい。単一起動制御とは別に、管理者権限起動を早期拒否するのが安全。
- 管理者権限拒否のダイアログはWails起動前に出す必要があるため、Win32の `MessageBoxW` などネイティブAPIを使うのが単純。
- 後続プロセスもWailsを起動していない段階で単一起動ダイアログを出す必要があるため、Wails runtimeの `MessageDialog` はそのまま使えない。
  - 単純な実装ならWin32の `MessageBoxW` を使えるが、標準ボタン名になりやすく、要件の日本語ラベルをそのまま出しにくい。
  - カスタムボタン名が必要なら `TaskDialogIndirect`、またはOSC/設定初期化を行わない最小preflight UIを別途用意する案がある。
- 既存ウィンドウのアクティブ化はWindowsのフォーカス奪取制限の影響を受ける。
  - Wailsの `WindowShow()` / `WindowUnminimise()` で表示復帰はできる見込みだが、前面化まで保証できるかは実機確認が必要。
  - 必要ならプロセスID/ウィンドウハンドルを使ったWin32 API呼び出しを追加で検討する。
- 「既存を閉じて新規を起動」では、既存側がOSC受信、キャプチャ、設定保存などを通常の終了処理で確実に止めてからmutexを解放する必要がある。
  - 後続プロセスは既存終了を待たずにOSC初期化へ進まない。
  - 将来 `beforeClose` で未保存確認を入れた場合は、IPC終了要求でもその挙動を尊重するか、別扱いにするかを決める必要がある。
- IPCは同一ユーザー以外からのshutdown要求を受けない設計にする。
  - 名前付きパイプならDACLで現在ユーザーに制限する。
  - localhost TCPを使う場合は、推測困難なtokenと、状態ファイルのユーザー限定権限が必要。
- 既存の `gofrs/flock` を残す場合でも、ロックファイルの場所は設定パスではなく固定のユーザーデータディレクトリへ移す必要がある。ただし、要求されたUXにはIPCが別途必要。
- 非Windows環境では既存のflockベースを維持するか、Windows専用実装としてbuild tagで分離する。OSCポート競合の主対象がWindows配布物である点を前提にする。

### 検証観点

- 管理者権限で起動した場合、通常ユーザー権限で起動するよう促すダイアログが出て、本体が起動しない。
- 管理者権限起動時に、設定ファイル作成、OSC初期化、IPC状態ファイル作成が行われない。
- 同一バージョンを別フォルダから起動しても単一起動になる。
- 別バージョンを別フォルダから起動しても単一起動になる。
- 既存が最小化されている状態で「既存をアクティブにする」を選ぶと表示復帰する。
- 既存が別ウィンドウの背後にある状態で、前面化の実効性を確認する。
- 「既存を閉じて新規を起動」を選んだ場合、既存のOSC受信が停止してから新規がOSC初期化へ進む。
- 既存プロセスが応答しない、状態ファイルだけ残っている、IPC接続に失敗する、などの異常系で誤って二重起動しない。
- `--version`、`--help`、zip暗号化処理を管理者権限拒否と単一起動制御の対象に含めるか除外するかを決め、決めた仕様どおりに動くことを確認する。
- Windows実機で、通常起動、zip配布物からの起動、異なる展開先からの起動を確認する。

## 実装内容

- `src/main.go` の設定パス依存 `ClipForVRChat.lock` を廃止し、GUI本体処理に入る前に `initializeSingleInstance()` を実行する。
- 単一起動ロックはユーザーキャッシュ配下の固定パス `ClipForVRChat/single-instance/ClipForVRChat.lock` へ移した。
  - 実行ファイルの配置パス、設定ファイルパス、バージョン文字列をロックキーに含めない。
  - OSのfile lockを使うため、プロセス終了後は古いlockファイルが残ってもロック自体は解放される。
- 先行プロセスは `127.0.0.1` の空きポートでtoken付きIPCサーバーを起動し、`single-instance.json` にPID、実行パス、バージョン、endpoint、tokenを保存する。
- 後続プロセスはロック取得失敗時に既存プロセスへ `ping` し、Windowsネイティブの起動前ダイアログで次を選択できる。
  - 「はい」: 既存プロセスへ `shutdown` を送り、ロック解放を待ってから新規プロセスを続行する。
  - 「いいえ」: 既存プロセスへ `activate` を送り、新規プロセスは終了する。
  - 「キャンセル」: 何もせず新規プロセスを終了する。
- 既存プロセス側の `activate` は Wails の `WindowShow`、`WindowUnminimise`、`Show` を呼ぶ。
- 既存プロセス側の `shutdown` は Wails の `runtime.Quit` を呼び、通常の `OnBeforeClose` / `OnShutdown` 経路で終了する。
- Windowsでは本体処理前にelevated tokenを検出し、管理者権限の場合はネイティブダイアログを表示して終了する。
- `--help`、`--version`、zip暗号化CLI処理は従来どおり単一起動制御と管理者権限拒否の対象外とする。

## 実装上の判断

- 当初候補のWindows named mutexではなく、既存依存の `gofrs/flock` によるユーザー固定パスfile lockを採用した。
  - 理由: 既存実装との差分を小さくしつつ、配置パス/設定パス依存を解消できるため。
  - 要件の「stale lockで起動不能にしない」は、lockファイルの存在ではなくOSロック取得可否を見ることで満たす。
- IPCはWindows名前付きパイプではなく、`127.0.0.1` + ランダムtokenを採用した。
  - 理由: Wails本体やテストと同じGo標準APIで実装でき、同一ユーザー固定ディレクトリ内の状態ファイルとtokenで誤操作を抑止できるため。
- この実装が入っていない旧バージョンは新しい固定ロック/IPCを作らないため、旧版が既に起動している状態を完全には制御できない。今回以降のビルド同士では、別フォルダ/別バージョンでも同じロックとIPCを見る。
